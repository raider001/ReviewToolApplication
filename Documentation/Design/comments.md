# Comment Design

## Overview

Git is the primary storage mechanism for comments. All comments are committed to the `kalynx-reviews` orphan branch and git remains the authoritative source of truth. The indexer maintains a lightweight routing index so connected clients know which repository's clone to read from and which comment changed.

---

## Design Principles

- **Git is primary** — all comments are written to the orphan branch first. No comment exists that is not also in git.
- **Indexer is a routing signal** — `GET /reviews/{reviewId}/comments` returns routing keys only (`repository_url`, `comment_id`). Comment content is always read from git.
- **Three streams per comment** — each comment has three independent append-only paths: `metadata` (written once), `text` (original + replies), `status` (resolution changes). This isolates conflict surface: only concurrent writes to the same sub-stream of the same comment can conflict.
- **Signal, not payload** — SSE events carry only `review_id`, `repository_url`, and `comment_id`. The client reads comment content from git after receiving the signal.

---

## Git Storage (Source of Truth)

### Location

Comments are stored on the `kalynx-reviews` orphan branch of the **specific repository the comment targets**. Each repository maintains its own orphan branch; a multi-repository review stores its comments on each participating repository's branch independently.

### Structure

```
refs/heads/kalynx-reviews   (on the repository the comment targets)
└── reviews/{reviewId}/
    └── comments/
        └── {comment-id}/
            ├── metadata    ← written once at comment creation
            ├── text        ← NDJSON append stream (original + replies)
            └── status      ← NDJSON append stream (resolution changes)
```

`{comment-id}` is a UUID v7 generated by the client when the comment is created. It is globally unique and is the sole primary key in `comments_index`. For the data format of each stream see [`datastructure.md`](datastructure.md).

### Write Semantics

- **`metadata`**: written exactly once. Contains the comment's location (file, line, commit). Never appended to after creation.
- **`text`**: append-only. First entry is the original comment; subsequent entries are replies. Each entry is one NDJSON line.
- **`status`**: append-only. Each entry records a resolution state change (resolved/unresolved). The latest entry wins.

Concurrent writes to **different comments** (different `comment-id`s) never conflict. Concurrent writes to the **same sub-stream** (e.g., two replies to the same comment at the same instant) are handled by retry: re-read the branch tip, re-append, re-push.

## Indexer Storage

The indexer maintains a `comments_index` table — one row per (review, repository, comment). It records that a comment exists and when it last changed. No comment content is stored in the DB. For the schema see [`ReviewToolCentralIndexer/Documentation/Design/storage.md`](../../ReviewToolCentralIndexer/Documentation/Design/storage.md).

When the indexer receives a push to `refs/heads/kalynx-reviews`, it:
1. Diffs the commit to find changed `reviews/{reviewId}/comments/{commentId}/*` paths
2. Determines event type from the sub-stream name: `metadata` or `text` → `comment.added`; `status` → `comment.updated`
3. Upserts `comments_index`
4. Fires one SSE event per changed comment

## Write Path

```
Client                      Git Remote              Indexer                 DB
  │                              │                      │                    │
  ├─ append to comment stream ───►                      │                    │
  │  (fire-and-forget push)      │                      │                    │
  │                              ├─ webhook push ───────►                    │
  │                              │                      ├─ upsert index ─────►
  │                              │                      ├─ SSE: comment.added │
  ◄─ SSE: comment.added ─────────────────────────────────┤                    │
  ├─ read sub-streams from clone ►                      │                    │
  ◄─ metadata + text + status ────┤                      │                    │
```

The optimistic local update (comment appears in UI immediately before the SSE round-trip completes) is handled at the client model layer.

---

## Read Path

### On initial review open

The client calls `GET /reviews/{reviewId}/comments` to get the list of `{repository_url, comment_id}` entries, then for each entry reads the three sub-streams from the appropriate clone in parallel.

### On SSE `comment.added` / `comment.updated`

The SSE event carries `{review_id, repository_url, comment_id}`. The client reads the relevant sub-streams from the named clone:
- `comment.added` → read `metadata`, `text`, and `status`
- `comment.updated` → read `status` only

For the full API and SSE event specifications see [`Interfaces/Client-Interface.md`](Interfaces/Client-Interface.md).

---

## Conflict Handling

Two clients writing to the same sub-stream simultaneously will result in a push rejection on the second writer. The write operation retries up to three times: re-fetch tip, re-append, re-push. In practice this requires two users to write to the exact same comment sub-stream within the same push window — extremely rare.

Two clients writing to **different comments** (different `comment-id`s) never conflict. Two clients writing to **different sub-streams of the same comment** (e.g., one adding a reply while another resolves) never conflict.
